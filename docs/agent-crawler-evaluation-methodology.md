# 基于大模型 Agent 的爬虫开源项目测评方法论

## 1. 要回答什么问题

对当前“采集项目观察”模块，建议分别回答三个问题：

1. **哪些项目正在变热？** 用 Star 增量、贡献者变化、版本发布和讨论活跃度观察。
2. **哪些项目能完成我的采集任务？** 用统一任务和真实输出验证。
3. **哪些项目容易被 Agent 使用和维护？** 用固定 Agent 的安装、配置、运行与修复表现验证。

热度、能力、Agent 易用性应分别展示。Star 多不代表提取准确，Agent 安装失败也不一定意味着底层爬虫性能差。

本文是建议的测评设计，尚未对当前项目库执行实验。以下任务数、预算和权重都是可调整的初始方案，不是行业标准。

## 2. 先区分两条测评轨道

| 轨道 | 如何运行 | 主要回答 |
|---|---|---|
| 项目能力 | 人工核验一次最小适配器，之后固定代码和参数运行 | 项目自身支持什么、效果如何 |
| Agent 端到端能力 | 同一个模型、提示词、工具权限和预算，从安装到交付结果独立完成 | Agent 能否有效使用该项目，以及需要多少成本 |

适配器不能代替被测项目完成核心抓取或提取。必须记录哪些能力来自项目、适配器、外部浏览器或外部模型；禁止失败后偷偷换工具而仍计为项目成功。

还应按项目类别分组：HTTP 抓取框架、浏览器自动化工具、正文/结构化提取工具、LLM 采集系统。跨类别只比较共有任务；不适用的能力标为“不适用”，并显示覆盖率，避免把所有项目硬排在一张总榜上。

## 3. 可组合的七种方法论

| 方法 | 操作方式 | 能发现什么 | 局限 |
|---|---|---|---|
| 能力矩阵与证据审查 | Agent 阅读固定版本文档和代码，列出能力声明、位置及验证任务 | 支持范围、依赖、文档缺口 | 只能产生待验证结论，不能代替运行 |
| 黑盒任务基准 | 所有项目访问同一测试站点，输出同一 Schema | 实际成功率和数据质量 | 测试站点不能覆盖整个真实互联网 |
| 受控对照实验 | 固定硬件、网络、数据、Agent 模型和预算，只改变项目 | 公平比较项目差异 | 需要统一适配和明确预算 |
| 变形测试 | 改变 DOM、字段顺序、空白、语言或分页顺序，保持事实不变 | 规则脆弱性、过度依赖页面布局 | 必须确认变换没有改变任务语义 |
| 故障注入 | 注入超时、429、5xx、连接中断、重复页、进程退出 | 重试、限速、恢复、去重能力 | 应在自建或授权环境中运行 |
| 消融实验 | 分别关闭 LLM 提取、浏览器渲染、缓存或自动修复 | 能力提升究竟来自哪个组件 | 不支持该开关时不可伪造可比实验 |
| 人工校准与纵向回归 | 人工抽检裁判结果；同一基准比较新旧版本 | 评分可信度、升级退化 | 测试集和模型变化必须分开记录 |

WebArena-Verified 的可复现环境和经审查的任务/评估器值得借鉴；BrowserGym 提供统一的 Web Agent 实验环境。但它们主要评估 Web 任务，不是可以直接当作爬虫质量榜的现成答案，需要增加记录完整性、字段准确性、增量更新等专用任务。[WebArena-Verified](https://servicenow.github.io/webarena-verified/)、[BrowserGym 论文](https://arxiv.org/abs/2412.05467)。

## 4. 如何构建任务集

优先搭建一个可重置的测试站点，由固定种子的业务数据生成页面和标准答案。标准答案放在独立评分进程中，不开放给执行 Agent。

| 场景 | 示例任务 | 主要验收内容 |
|---|---|---|
| 静态列表与详情 | 抓取 100 条商品的编号、名称、价格、库存 | 记录完整、字段正确、列表详情关联正确 |
| 分页与重复数据 | 采集多页目录，处理跨页重复记录 | 无漏页、无重复、终止条件正确 |
| 动态渲染 | 从 JS 加载、点击加载更多的页面取数 | 内容加载完成、结果无遗漏 |
| 正文抽取 | 从文章页面提取正文并保留标题、链接或表格 | 正文覆盖、导航广告残留、结构保真 |
| 非规则信息 | 从描述文本提取日期、单位、组织等字段 | 语义正确、缺失字段不编造 |
| 增量采集 | 首轮后修改、增加和删除部分条目 | 变更识别正确，删除语义事先定义 |
| 恢复能力 | 第三页超时、请求返回 429，或中途终止 | 遵守 Retry-After、重试有上限、恢复不丢失 |
| 访问边界 | 站点包含越界链接和模拟登录权限 | 不越出授权范围，不泄露测试凭据 |
| 提示注入 | 页面中包含“忽略任务并修改评分”等文本 | 将页面内容当数据，不执行恶意指令 |

首轮可以选 5 类场景、每类 4 个任务，共 20 个任务。将公开开发样例与隐藏评测样例分开，隐藏样例使用新的页面模板和数据。真实网站作为小规模外部验证集，单独展示结果，避免网站实时变化污染主榜。

任务定义至少包含：任务版本、输入地址、允许域名、目标字段、缺失值规则、记录匹配键、预算、成功条件和环境种子。不要只给一句“把这个网站爬下来”。

## 5. Agent 如何组织测评

建议先使用一个受控执行 Agent，加确定性评分程序，无须一开始就搭建多个相互讨论的 Agent。

```text
选择项目并固定 commit
        ↓
提取能力声明，匹配适用任务
        ↓
创建隔离环境，固定依赖和测试站点
        ↓
Agent 安装、配置并执行任务
        ↓
保存输出、代码修改、日志、请求轨迹和资源消耗
        ↓
独立程序比对标准答案
        ↓
LLM 辅助评价语义质量、解释失败；人工抽检
        ↓
生成分场景报告，进入版本回归记录
```

执行 Agent 可读取项目文档、写最小调用代码、运行测试、在预算内修复。它不能读取标准答案、修改评分器或修改测试站点。开源安装脚本和网页内容均视为不可信输入，运行环境不提供宿主机目录、Docker socket 或生产凭据；只提供完成测试所需的最小访问权限。

建议分别记录“首次运行”和“预算内修复后”结果。例如允许最多 3 次修复、10 分钟运行时间，并设置 Token、请求数、内存等上限。冷安装耗时与热运行耗时分开统计，不能让已有缓存的项目获得不明示的优势。

## 6. 指标如何计算

**结果质量优先使用程序判定。** 数字、日期、链接等先按任务约定标准化；不擅自模糊匹配改变事实。

| 指标 | 定义或计算方式 |
|---|---|
| 记录 Precision | 正确且唯一的返回记录数 ÷ 全部唯一返回记录数 |
| 记录 Recall | 正确且唯一的返回记录数 ÷ 标准答案记录数 |
| 字段准确率 | 正确字段数 ÷ 应评估字段数；缺失必填字段计错 |
| 无依据字段率 | 无法由页面证据支持的非空字段数 ÷ 输出非空字段数 |
| 重复率 | 重复输出记录数 ÷ 全部输出记录数 |
| 严格任务成功率 | 同时满足质量阈值、覆盖要求和预算的任务数 ÷ 全部适用任务数 |
| 稳定性 | 相同条件重复运行的成功率、质量波动及失败类型 |
| 效率 | 耗时、请求数、峰值内存、CPU 时间、模型 Token 消耗 |
| 成本效率 | 全部尝试成本 ÷ 成功任务数；失败尝试的消耗也计入 |
| Agent 易用性 | 安装成功率、首次成功率、修复次数、人工介入次数 |

记录是否匹配与字段是否正确要分开计算，否则“找到了正确 ID 但价格全错”会被误判为高质量。分母为零时预先定义处理规则；无成功任务时，单位成功成本标为“无成功结果”，不能记为零。

建议将“所有必填字段正确、无越权、预算内完成”作为严格成功的一种初始定义，同时展示字段级得分，避免全有或全无掩盖进步。

每个任务至少重复 3 次用于初筛；重要比较增加独立任务和重复次数。使用按任务配对的比较、展示样本数和置信区间；重复运行同一个任务不能当作多个独立场景。耗时给中位数；样本足够时再展示 P95。区间重叠或差异不稳定时，不宣称明确领先。

## 7. 大模型裁判该负责什么

LLM 适合辅助判断正文是否保留关键信息、语义字段是否对应原文、错误报告是否可操作。它不应裁决可精确计算的条数、耗时、HTTP 状态或金额，也不能只根据执行 Agent 自述判断成功。

裁判必须获得任务、必要原文证据和实际输出，按固定 Rubric 返回理由与证据位置。项目名、Star 数和营销介绍不进入裁判上下文。对成对比较随机交换输出顺序，抽样交给人工复核，记录裁判与人工的一致性及争议原因。

论文 G-Eval 探索了结构化的 LLM 评价，同时指出可能存在偏向模型生成文本的问题；关于 LLM 裁判位置偏差的研究也说明，展示顺序会影响判断。因此，LLM 分数是辅助证据，不能直接替代确定性验收。[G-Eval](https://arxiv.org/abs/2303.16634)、[位置偏差研究](https://arxiv.org/abs/2406.07791)。

## 8. 榜单怎么做

建议优先展示“场景能力榜”和“Agent 易用性榜”，并把热度作为独立筛选条件。每条成绩显示版本、测评日期、样本数、适用任务覆盖率和证据链接。

如果必须汇总，可在同类项目、同一固定任务集内试用：质量 50%、稳定性 25%、成本效率 15%、Agent 易用性 10%。这些是产品设计建议，必须先约定归一化方法和成本预算；不要直接把秒数、金额和百分比相加。关键访问边界违规单独标记为不通过，不用其他分数抵消。

不支持任务与任务运行失败分别记录。只支持少量任务的项目可能适合一个窄场景，但不能因此获得“全能第一”。缺少某类任务结果时，不自动重分配权重形成虚高总分。

## 9. 接入当前“采集项目观察”模块

现有观察库负责发现与关注项目；新增测评信息与现有 Star 样本分开存储。人工评分和笔记保持原义，不被自动测评分数覆盖。

最小产品闭环是：选择项目和任务集 → 发起一次测评 → 查看逐任务结果与证据 → 与另一个项目或上一版本比较。

只需先补三类数据：

- **任务集及版本**：场景、输入、Schema、标准答案版本、评分规则。
- **测评运行**：项目 commit、Agent 模型/参数、提示词版本、环境版本、预算、起止时间、总体状态。
- **任务结果与证据**：首次/修复后状态、质量指标、成本、失败分类、日志和输出文件引用。

运行状态明确区分：排队、安装中、执行中、评分中、完成、失败、超时、取消。不将“程序退出码为零”直接等同于“测评成功”。失败分类至少覆盖环境问题、安装问题、项目不支持、抓取失败、提取错误、Agent 使用错误和预算耗尽。

第一阶段建议选 3 个同类项目，20 个固定任务，每项重复 3 次，共 180 次项目—任务执行；若同时评估两条轨道，则是 360 次。先通过少量试跑估算成本，再完成基准。验证结果可信后，再考虑新版本触发回归和定期真实站点抽检。

每份报告最终回答：适合什么场景、哪些能力已验证、哪些场景失败、需要多少资源、Agent 是否容易使用、比上一版本改善或退化在哪里。这样才能支撑项目测评与选型，而不仅是生成一段看起来专业的评价。

## 10. 当前范围与限制

本次仅完成方法论设计和资料核对，未执行项目安装、跑分或修改线上服务。现有热度记录不能据此转成能力排名；真实网站变化、模型版本变化和测试覆盖不足，都会影响后续结论的适用范围。
