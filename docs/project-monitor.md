# 项目动态监测

入口：采集项目观察 → 查看版本与问题动态（`/crawler-watch/updates`）。

## 使用

1. 在采集项目观察列表中关注项目，手动添加的项目默认关注。
2. 打开项目动态，点击“立即检查动态”；启用 `SCHEDULE_ENABLED` 的服务也会每 6 小时检查。
3. 首次同步建立历史基线，不制造未读提醒。后续出现新 Release、Issue，或标题、正文、标签、开闭状态变化时标为未读。
4. 可按项目、Release/Issue、未读筛选，查看来源原文和最近 20 次变化记录。标为已读不会隐藏未来更新。
5. 项目检查状态展示最近完整同步时间、Release 时间及未完成分页/错误；限流时保留进度，遵守共享冷却时间后重试。

已读状态由当前部署共享。取消关注或隐藏后停止检查，不删除历史记录及测评笔记。

## 解释边界

- 发布说明是项目作者的声明，尚未经真实运行验证。
- Issue 包括问题、需求和讨论；开放不代表确认存在缺陷，关闭不代表已修复或已经发布修复。
- 不自动把 Release 与 Issue 关联，不推断影响版本，也不自动执行第三方项目代码。
- 不调用大模型对不确定信息自动下结论；不发送邮件、即时通讯或浏览器推送。
- 仅检查公开仓库，忽略草稿 Release 和 Issue 列表中的 PR。
- Release 每轮读取最近 30 条；不监测窗口之外旧版本的编辑或删除。
- Issue 初次回溯最近 30 天更新的记录，后续增量读取；每个项目每轮最多 3 页、每页 100 条（含被过滤的 PR），超出时续传。列表不是 GitHub 的原子快照，通过时间重叠和去重降低变更期间的遗漏，不能保证瞬时创建又删除的内容一定被捕获。
- 评论数变化不会单独提醒，不抓取评论正文或判断维护者身份。

## 存储与运行

新增 `monitor_states`、`monitor_events`、`monitor_runs` 表。启动时通过现有数据库初始化创建，不修改既有项目、Star 样本和人工笔记。共用现有采集任务锁、后台线程和 GitHub 限流冷却；调度优先处理关注动态。

新增接口：

- `GET /api/watch/monitor`：执行、项目同步、调度及冷却状态。
- `POST /api/watch/monitor/refresh`：手动检查关注项目，正文 `{}`。
- `GET /api/watch/events`：动态筛选与分页。
- `POST /api/watch/events/{id}/read`：正文包含客户端看到的 `changed_at`，过期版本返回 409，避免抹掉刚到达的更新。

同步失败不清空已有内容，分页和该页数据在同一事务中提交；每条来源通过项目 ID、类型和 GitHub ID 去重。同步与已读操作均锁定事件记录，避免并发更新丢失未读标记。

建议为 GitHub API 配置 Token 以降低限流影响，凭据仅放部署环境变量，不写入仓库。未配置 Token 仍可读取公开数据，但实际更新频率受额度与任务耗时影响。

参考：[Release API](https://docs.github.com/en/rest/releases/releases)、[Issue API](https://docs.github.com/en/rest/issues/issues)。
