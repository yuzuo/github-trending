# 爬虫与数据采集项目观察站 · 设计提案

日期：2026-10-14

状态：用户已确认并实现；交付验证见 ../../verification.md

## 目标

新增独立的“采集项目观察”页面，保存爬虫、网页提取和数据采集相关 GitHub 项目，支持发现热门项目、持续监测和记录人工测评。

“热门”同时展示累计关注度和近期增长，默认按近 7 天新增 Stars 排序，不用总 Stars 代替近期热度。不承诺覆盖 GitHub 全站相关项目。

## 方案比较

| 方案 | 优点 | 局限 |
| --- | --- | --- |
| 仅手动收藏 | 实现简单、项目范围准确 | 无法主动发现新项目 |
| 自动发现＋手动关注＋测评记录（推荐） | 同时支持发现、持续监测和测评 | 需要定期调用 GitHub 并积累历史 |
| 全量领域采集与实时预警 | 覆盖更广、更新更快 | 请求量及运维复杂度大，不适合当前本地应用 |

## 页面与操作

- 新入口 `/crawler-watch`，沿用现有顶部导航和视觉样式。
- 提供“全部项目”“我的关注”“待测评”筛选，以及关键词、开发语言筛选。
- 提供近 7 天新增 Stars、近 24 小时新增 Stars、累计 Stars 排序。
- 列表展示名称、简介、语言、累计 Stars、两种增长量、最近推送时间、最近监测时间、关注与测评状态。
- 支持粘贴 GitHub 仓库地址或 `owner/repo` 手动添加，服务端校验并查询仓库是否存在、是否公开。
- 支持关注/取消关注、隐藏自动发现的无关项目；隐藏保留历史与测评资料，不自动重新展示。
- 详情展示项目基本资料、README 原文、监测历史表格和人工测评记录。
- 测评状态为“待测评 / 测评中 / 已测评 / 暂不考虑”；支持可选的 1–5 分评分和纯文本笔记，显式保存并反馈成功或失败。
- 默认不调用模型为新模块翻译或自动测评；评分来自用户判断，不根据 Stars 推导质量。

## 自动发现

- 每天执行一次 GitHub 官方 Search API 发现，使用固定主题 `web-scraping`、`crawler`、`data-extraction`，以及名称/描述关键词 `web scraping`、`爬虫`、`数据采集`。
- 每条查询分别取累计 Stars 最高的前 30 个、最近更新的前 20 个；默认排除 fork 和已归档仓库。
- 按 GitHub 数字 ID 去重，记录命中主题或关键词，便于判断相关性；关键词匹配属于候选发现，不声称自动分类完全准确。
- 最多同时监测 200 个项目。优先保留手动添加和已关注项目，其余按候选累计 Stars 填补名额；满额时提示可隐藏无关项目释放名额。
- 不因未再次命中搜索而删除已有项目。被隐藏项目停止监测，资料仍可恢复。
- 手动添加不受发现主题限制，但受公开仓库和总容量限制；达到上限时明确拒绝，不静默挤掉关注项目。
- 不在启动时直接写入上一轮聊天中的 Star 数；所有数值来自实际 GitHub 请求。

## 监测频率与热度口径

- 默认每 6 小时更新全部活动监测项目；提供“立即更新”按钮。
- 自动调度遵守现有总开关，设备和服务需持续运行。
- 每次成功采集保存项目 ID、采集时间和累计 Stars；同一个任务重试不重复生成成功样本。
- 增长量为最新观测值减去基准观测值，允许负数，不将减少量归零。
- 24 小时基准：选取不晚于最新观测时间减 24 小时、且距离该目标不超过 6 小时的最近样本。
- 7 天基准：采用同样规则，目标为最新观测时间减 7 天。
- 无有效基准时显示“积累中”或“缺少基准”，不能显示 0 或据此外推增长；该排序下缺少指标的项目置后。
- 展示实际观测区间；这是约 24 小时/7 天的净增长，不是 GitHub Trending 的来源统计值。
- 距离当前时间超过 12 小时的最新样本标记“数据过期”，默认增长榜放在新鲜数据之后，避免旧数据被误判为当前热度。
- 首日可按累计 Stars 查看，完整 7 天增长需积累至少 7 天的有效数据。
- 第一版通过页面展示新增发现、增长排名和更新时间，不包含邮件、微信或系统推送，也不自动运行仓库代码做测评。

## 实现范围

- 后端：增加观察项目、Star 观测样本及独立任务记录；项目记录保存关注、隐藏、测评状态、评分、笔记、最新资料及发现依据。
- 观察数据独立保存，避免改变现有两榜的每日冻结规则；无需将其作为第三种每日快照来源硬塞入现有接口。
- 增加列表、详情、添加、编辑、触发更新及任务状态接口；复用已有 GitHub 请求、脱敏、README 渲染和同源写入保护。
- 调度接入现有后台生命周期，共享采集互斥与 GitHub 冷却机制；原有两榜任务优先，观察任务繁忙时延后执行。
- 数据库仅新增表及必要约束，不删除或重写已有榜单记录。仓库数字 ID 唯一，地址更名后更新显示名称。
- 前端使用独立 Vue 组件承载新增页面，避免继续扩张榜单页面；更新导航和路由选择。
- 更新配置示例、README 和产品文档，写明监测频率、容量和增长口径。

## 失败与安全边界

- 单仓库失败保留最近成功资料并展示失败提示，不写入伪造样本；其他项目继续处理。
- 搜索不完整不视为完整发现结果，不删除已有项目；独立查询失败可报告部分完成。
- 限流遵守 GitHub 冷却时间，手动按钮不能绕过冷却或同时启动多个任务。
- 重启后将遗留运行任务标记中断；恢复后按调度规则继续。
- 输入只能指向公开 GitHub 仓库，不能通过自定义 URL 请求任意内网地址。
- 测评笔记采用纯文本显示；README 复用现有 HTML 清洗。不增加对外消息发送或新收费服务。
- 当前无账号系统，测评笔记属于该部署的共享数据，能够访问应用的人可查看和编辑。

## 验收与测试

1. 原有 Trending 和 Star 总榜查询、采集、历史快照不受影响。
2. 同仓库重复发现或重复手动添加不会重复建立项目。
3. 自动发现、手动添加、关注、隐藏、恢复和容量上限可验证。
4. 用固定时间样本验证 24 小时/7 天差值、负增长、缺基准、停机间隔及过期数据排序。
5. 新项目没有历史时不显示伪造的增长量；页面清楚标注新鲜度和观测区间。
6. 测评状态、评分、笔记保存后刷新仍保留；无效评分及非法仓库输入被拒绝。
7. 任务互斥、冷却、失败保留旧数据及进程重启恢复有后端测试。
8. PostgreSQL 验证新表、唯一约束、指标查询和原有数据保留；前端验证主要状态并构建。
9. 真实 GitHub 联调单独报告，不将模拟请求通过当作外部服务实测通过。
